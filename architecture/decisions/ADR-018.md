# ADR-018: Patient bounded retries for transient provider unavailability

## Status

Accepted, 24 November 2026, after the submission deadline. Amends the retry/backoff constants listed under ADR-009; stage checks, budgets and model tiering are unchanged.

## Context

Hosted corrected runs repeatedly died inside brief free-tier outages. A3 run 45277567719 (24 November, 03:43 IST) completed one real SpecWriter call and failed when the next calls hit HTTP 503 high-demand spikes; the fixed policy (API_RETRIES=2, backoff 15/30s, about 45 seconds of tolerance per tier) was exhausted in roughly 90 seconds. Run 45279778860 (03:57 IST) repeated the pattern after three real calls. Availability probes between the runs succeeded, showing the outages were multi-minute spikes, not sustained downtime. Waiting inside the run costs no tokens; only completed calls are recorded as usage, though a failed call may still be billed by the provider and is reported as an attempt, not as successful usage.

## Decision

Make the retry policy configurable and patient by default: API_RETRIES and API_BACKOFF_SECONDS read from the environment with defaults of 3 retries and 30/60/120 second backoff, so each model tier tolerates about three and a half minutes of continuous outage before the run falls back to the alternate tier, and roughly seven minutes before the stage fails. Per-tier patience is deliberately short so a flapping model is abandoned for the working alternative quickly; stage job timeouts (30 to 60 minutes) leave room for several slowed calls. The per-run token budget (MAX_TOKENS_PER_RUN), the 40-step cap and every stage check are unchanged; a stage that still exhausts both tiers fails exactly as before, with its failure artifact.

## Alternatives

- Keep short retries and retrigger whole runs by hand: each retrigger repeats gate work and discards in-progress stage state, and overnight spikes make manual timing a lottery.
- Unbounded retries: an unresponsive provider would hold the runner for hours and blur the line between a slow run and a stuck one (ADR-009 requires visible budgets).
- Exponential backoff without a cap: same stuck-run risk.

## Consequences

Runs ride out short spikes without operator involvement, which is what the corrected contract needed for overnight free-tier execution. During a sustained outage a stage now takes up to about seven minutes per call to fail instead of ninety seconds, which delays the failure signal but never converts it into a pass. The constants remain visible in config.py next to the other budgets and can be tuned through repository variables without another code change.

Offline regression tests pin the patient defaults, the environment override parsing, the per-tier retry counts and the no-fallback path after a short spike. These tests do not establish provider availability or any end-to-end issue outcome.
